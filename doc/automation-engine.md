# Automation engine

## Purpose
Background service that watches each project for events and dispatches agents in response. Drives the agentic workflow: when a ticket moves, a comment is posted, a commit lands, an interval elapses, etc., the engine evaluates configured automations and runs the matching actions.

## Key components
- `GigaClaw.Core/Automation/AutomationEngine.cs` — top-level wiring only; delegates to `TriggerHandler` and `RunStateManager`.
- `GigaClaw.Core/Automation/TriggerHandler.cs` — owns the tick loop (urgent drain + per-project poll).
- `GigaClaw.Core/Automation/RunStateManager.cs` — encapsulates the 5 dispatch-gate checks (`ShouldSkipAsync`); shared by `AutomationEngine` and `ActionExecutor`.
- `GigaClaw.Core/Automation/ActionExecutor.cs` — condition evaluation and all `Execute*Async` action implementations; delegates skip checks to `RunStateManager`. Holds `_inFlightChains` (`ConcurrentDictionary` keyed by `"{automationId}:{ticketId}"`) to serialize action chains per (automation, ticket) pair — a second firing is dropped while one is already in progress.
- `GigaClaw.Core/Automation/ProjectRuntimeManager.cs` — per-project runtime dictionary and signal fan-out.
- `GigaClaw.Core/Automation/ProjectRuntime.cs` — data class holding per-project run state.
- `GigaClaw.Core/Automation/AutomationConfig.cs` — JSON-deserialized automation definitions (triggers, conditions, actions).
- `GigaClaw.Core/Automation/AutomationStore.cs` — loads/persists `automations.json` from each workspace's `.agents/` folder, and validates the optional `workflow.json` beside it at the same load point (see [Workflow graph](./workflow-graph.md)). An invalid graph fails the reload as a whole, exactly as a malformed `automations.json` does.
- `GigaClaw.Core/Automation/Triggers/` — trigger implementations.
- `GigaClaw.Core/Automation/GitRepositoryWatcher.cs` — backs the `gitCommit` trigger.
- `GigaClaw.Core/Automation/RunConcurrencyGate.cs` — serializes runs sharing a `concurrencyGroup`.
- `GigaClaw.Core/Automation/ConcurrencyLockReaper.cs` — background service polling every 30s; force-stops any `runAgent` run that has been idle past its `RunAgentActionSpec.LockTimeoutMinutes` (opt-in per-automation). Idleness is measured via `AgentRun.LastActivityAt` (heartbeat updated on every streamed event). Prevents a hung subprocess from holding a `concurrencyGroup` lock forever and starving later dispatches.
- `GigaClaw.Core/Automation/TriggerStateStore.cs` — persists each interval/cron automation's next scheduled fire time (`NextRunAt`) in the per-project SQLite DB (`automation_trigger_state` table). Computed once at registration and saved immediately (not recomputed from "now" on every tick), so a restart that straddles the scheduled moment still fires on time; a missed occurrence catches up with a single immediate fire on the next tick.

## Model
- **Triggers**: `interval`, `ticketInColumn`, `statusChange`, `subTicketStatus`, `ticketCommentAdded`, `gitCommit`, `boardIdle`, `agentInactivity`.
- **Conditions**: `ticketInColumn`, `ticketCountInColumn`, `fieldLength`, `priority`, `labels`, `assignedTo`, `hasParent`, `allSubTicketsInStatus`, `ticketAge`, plus `verdictIs`, `repairBudget` and `reviewerRetryBudget` (all three explained in the [verdict contract](./verdict-contract.md)).
- **Actions**: `runAgent`, `moveTicketStatus`, `setLabels`, `assignTicket`, `addComment`, `consolidateAgentMemory`, `commitAgentMemory`, `executePowerShell`, `createTicket`, `httpRequest`.
- **Conditions**: `ticketInColumn`, `ticketCountInColumn`, `fieldLength`, `priority`, `labels`, `assignedTo`, `hasParent`, `allSubTicketsInStatus`, `ticketAge`.
- **Actions**: `runAgent`, `moveTicketStatus`, `setLabels`, `assignTicket`, `addComment`, `consolidateAgentMemory`, `commitAgentMemory`, `executePowerShell`, `createTicket`, `httpRequest`, `startTeamRun`, `parallelRunAgents`, `startWorkflow`.
- **`startTeamRun`**: starts a run of the named team definition on the firing ticket — one sub-ticket per task template, assigned to the role's agent, ordered by ordinary ticket dependency edges. Idempotent per (ticket, team). It only *starts* the run; the sub-tickets are then dispatched by the ordinary per-agent automations, and ordering, release, the join, the synthesizer and cancellation are driven from the board by the reconcile pass at the top of each tick. See [Executable teams](./executable-teams.md).
- **`parallelRunAgents`**: the same machinery with the branches declared inline instead of stored — per-branch agent and prompt, `maxConcurrency`, a `join` policy (`allDone` / `quorum` / `firstFailure`), `onPartialFailure` (`synthesize` with the gaps named, or `failFast`), and an optional `synthesizer`. It is *executed as* an ad-hoc team run: the action materializes a `TeamDefinition` snapshot rather than adding a second execution engine, so fan-out, join semantics, cancellation propagation and restart resume are the ones described in [Executable teams](./executable-teams.md). Branches are sub-tickets started by the ordinary per-agent automations, which is what makes each one queue behind `RunConcurrencyGate` and take its file leases. Idempotent per (ticket, `runSlug`).
- **`startWorkflow`**: opens a walk of the workspace's declared workflow graph on the firing ticket. Like `enqueueMerge` it only records intent — the engine's own per-tick walker enters the states, materializes each `task` state as a sub-ticket the ordinary per-agent automations dispatch, routes `gate` states through the ordinary conditions, runs `fanOut` as an ad-hoc team run, bounds the cycles and parks the ticket with a receipt on anything undecidable. Idempotent per ticket. See [Workflow graph](./workflow-graph.md).
- **`httpRequest`**: calls an outbound webhook/API. `url`, `bodyTemplate` and header values are templated. `secretRef` names an **environment variable on the GigaClaw server process**, resolved at execution time and injected as `Authorization: Bearer <value>` unless an explicit `Authorization` header is set; only the variable name is persisted to `automations.json`, never the token, and the token is never logged. A missing variable logs a warning and the request proceeds unauthenticated. Like `consolidateAgentMemory` and `executePowerShell`, it detaches the rest of the chain onto a background task so network I/O cannot stall the engine tick.
- **Chain values (output → input)**: `httpRequest` publishes `{http.status}`, `{http.body}` (raw, trimmed, capped at 8 KB) and one `{http.body.<field>}` per first-level field of a JSON-object response into the chain's `ActionState.ChainValues`. Later actions in the same chain — including post-run actions after a `runAgent` — render them via the shared `ActionTemplate.Render` helper, which is how a CMS receipt (`{http.body.adminUrl}`) gets written back as a ticket comment. Chain values live only for the duration of one chain and are never persisted. Unknown placeholders are always left verbatim.
- **`executePowerShell` placeholders and chain values**: `Script`/`ScriptFile` and every entry in `Arguments` are templated with `{ticketId}`, `{ticketTitle}`, `{slug}`, plus any chain value published earlier in the same chain (e.g. `{http.body.adminUrl}` from a preceding `httpRequest` — chain values are a single shared bag, not scoped to the action type that published them). `{draft.*}` is deliberately **not** wired here: those values are JSON-escaped for splicing into an `httpRequest` `BodyTemplate` and are not safe to hand to a shell verbatim; a script that needs the draft fetches and parses the ticket itself via the GigaClaw API. On completion (success, non-zero exit, or timeout) the executor publishes the trimmed stdout and exit code back into the chain as `{powershell.stdout}` (capped at 4 KB) and `{powershell.exitCode}`, mirroring `httpRequest`'s `{http.status}`/`{http.body}` — this is how a script's outcome (e.g. an archive step) reaches a follow-up `addComment`. Inline `Script` + `Arguments` is routed through a temp `.ps1` file rather than `-EncodedCommand`, since PowerShell only exposes trailing positional arguments as `$args` for `-File`.
- `{assignee}` placeholder in `runAgent.agent` / `runAgent.concurrencyGroup` resolves from the firing ticket's `assignedTo`.
- `{ticketId}` placeholder in `concurrencyGroup` and `mutuallyExclusiveWith` resolves to the firing ticket's ID, enabling per-ticket serialization while preserving parallelism across distinct tickets.
- `commitAgentMemory` detects whether `.agents/` is a standalone git repo (`.agents/.git` present) and commits there; otherwise falls back to the main workspace repo. It commits both the per-topic memory layout (`.agents/{agent}/memory/`) and any legacy flat `.agents/{agent}/memory.md`.
- Canonical post-run chain: `runAgent` → `consolidateAgentMemory` → `commitAgentMemory`.
- **`statusChange` trigger re-fire on failure**: for `runAgent` actions backed by a `statusChange` (or `subTicketStatus`) trigger, `ActionExecutor` defers advancing the trigger snapshot (`commitAsync`) until after the run completes. If the run ends with `AgentRunStatus.Failed` or `Stopped`, the snapshot is left at the pre-transition value, so the next poll detects the transition again and re-dispatches the agent. On `Completed`, the snapshot advances normally and subsequent polls stay silent. This means a rate-limited or crashed agent is automatically retried on the next poll cycle (≤ `pollSeconds`) without any manual intervention.
- **Status snapshots are isolated per automation**: each `statusChange` rule owns its persisted acknowledgement state. A successful lightweight rule can no longer acknowledge the same transition on behalf of a different rule that was skipped by a concurrency or budget gate. Existing workspaces lazily seed each isolated snapshot from the legacy shared snapshot.
- **Bounded `ticketInColumn` retries**: `maxConsecutiveFirings` limits completed chains for an unchanged ticket, while `retryBackoffSeconds` persists a cooldown across restarts. Status, assignee, title, or description changes reset the series; comments and `UpdatedAt` churn do not. Optional `exhaustedStatus`, `exhaustedAssignee` and `exhaustedComment` escalate exactly once when the cap is reached — the reassignment is applied first, so the ticket never appears in its new column still owned by the agent that gave up on it, and an `exhaustedAssignee` that is not a member of the project is skipped rather than aborting the move. Point it at a triage agent, never at the agent the same automation dispatches, or exhaustion feeds straight back into the dispatch that failed. Set `maxConsecutiveFirings` to `0` only for an intentional unbounded workflow.
- **`unassigned`**: narrows a `ticketInColumn` trigger to tickets with no assignee at all. `assigneeSlug` cannot express this — an empty slug there means *any* assignee — so this is what lets an intake automation and a per-agent automation watch the same column without fighting over the same tickets. Setting both is contradictory and matches nothing.
- **Completion recorded after the whole chain**: `ITrigger.CompleteFiringAsync` receives the final success/failure outcome after status restoration and all post-run actions. Automation-owned runs keep their registry status at `Running` until this bookkeeping is complete, so observers cannot see a terminal run while its ticket/trigger state is still unsettled.
- **Debounce stamped at chain completion**: successful legacy triggers still commit through `ITrigger.CommitFiringAsync`; `ActionExecutor` passes `DateTime.UtcNow` at the moment the entire action chain finishes. Interval/cron debounce timestamps therefore reflect chain completion time rather than emission time.
- **Atomic label actions**: `setLabels` creates missing label definitions and applies additions/removals through one ticket mutation. A label mutation failure fails the action chain instead of being logged as a false success.

## Spend gates

Two config-level ceilings sit in `automations.json` beside the automation list itself, and both are enforced in `RunStateManager.ShouldSkipAsync` before any `runAgent` dispatch:

- **`dailyBudgetUsd`** — project-wide daily spend, measured by `CostTracker` against `.agents/channel/cost-log.jsonl`. The `ceo` concurrency group is exempt. When the day's spend reaches the cap, dispatches are skipped and the automation is simply quiet until the next UTC day.
- **`maxTicketCostUsd`** — the per-ticket sibling. The daily budget stops the whole project once the day's money is gone, which is no help against a single ticket that loops an agent all afternoon while the rest of the board stays cheap. Measured against that ticket's own durable `Ticket.AgentCostUsd` column (written by `RunCostRecorder` → `TicketService.AddAgentUsageAsync`), so it survives a restart and no engine-side counter can drift from it. Omitting the key is the only way to disable it; every value from `0` up is enforced, and `0` means "this ticket gets no further spend" rather than "unlimited". `ProjectTemplate/Agents/automations.json` ships `"maxTicketCostUsd": 25.00` so a new project is bounded from its first dispatch — it is a ceiling to raise deliberately, not a target.

  This matters most for the re-scoping loops. Exhaustion routes a ticket to `Backlog` owned by the `groomer`, and that hand-off resets both of the counters that bound it: `ticketInColumn` clears its attempt series when the ticket's fingerprint changes, and the repair budget is recounted from the last escalation receipt. The `triaged` label caps the loop at one automated lap (see the [verdict contract](./verdict-contract.md)); `maxTicketCostUsd` caps what any single ticket can spend getting there.

  On a breach the dispatch is skipped, one `GIGACLAW-COSTCAP v1` receipt is posted, and the ticket is assigned to `groomer` so it is owned rather than orphaned. The receipt is written **at most once per episode**, keyed on the cap value it names — the state lives nowhere but the ticket's comment trail, the same stateless recount `repairBudget` and `reviewerRetryBudget` use — so a 30-second `ticketInColumn` trigger re-evaluating a parked ticket cannot bury it in comments, while raising the cap opens a fresh episode that may report again.

  The cap has **no agent exemption, not even for the triage agent it hands the ticket to**. Exempting `groomer` reads as an obvious kindness — the point of the hand-off *is* re-scoping — but it builds a funded loop: over-cap ticket → assigned to groomer → groomer runs (billed) → groomer re-routes to the producing agent → that dispatch is skipped for being over cap → back to groomer. Each lap costs money and nothing about the ticket changed. A cap with an exemption is a suggestion, so the breach is a hard stop: work resumes only when a human splits the ticket, raises `maxTicketCostUsd`, or closes it. See `GigaClaw.Core/Automation/TicketCostCap.cs`.

Both ceilings surface in the cross-project attention queue on [Mission Control](./mission-control.md): the daily budget as an alert past 80% of the cap, and a cost-capped ticket as its own row (a parked ticket is otherwise invisible — it just stops moving).

## Draft archival (Task 16 / AD-7)

Content-pipeline projects append two things to `cms-dispatch-on-done`'s `httpRequest` → `setLabels` → `addComment` receipt: an `executePowerShell` step running `.agents/scripts/archive-draft.ps1`, then a follow-up `addComment` posting `{powershell.stdout}` — the script's one-line summary — onto the ticket, alongside the CMS receipt already posted by the prior step.

- **Best-effort, never blocking.** The archive step's `abortOnFailure` is `false`, and it runs *after* the `dispatched` label and CMS receipt — dispatch integrity is sealed before archival is ever attempted. The script itself also always exits `0`: a missing `GIGACLAW_ARCHIVE_ROOT`, an unreachable API, or a failed `git commit` each print a warning to stderr and a one-line explanation to stdout, never a hard failure.
- **Self-fetching, not template-fed.** The script receives only `{ticketId}`, `{slug}` (the project slug) and `{http.body.adminUrl}` as arguments — small, shell-safe values. It fetches the ticket's `description` itself from `${GIGACLAW_API_URL:-http://localhost:5230}/api/projects/{slug}/tickets/{id}` and re-parses the AD-7 frontmatter for `slug`/`title`, rather than receiving `{draft.*}` (see the `executePowerShell` placeholder note above for why).
- **Target path**: `$GIGACLAW_ARCHIVE_ROOT/<projectSlug>/<yyyy-MM>/<slug-or-ticket-id>.md` — the frontmatter and body are written verbatim, with `ticket-id`, `cms-admin-url` (when passed) and `archived-at` appended below a `---` rule. If `GIGACLAW_ARCHIVE_ROOT` points into a git working tree, the new file is `git add`ed and committed (author `GigaClaw <automation@gigaclaw.local>`); a commit failure is logged and otherwise ignored.
- **Vault-agnostic.** `GIGACLAW_ARCHIVE_ROOT` can point at an Obsidian vault (the decided default target — trivially git-backed, continuous with the ZabsAIOS vault) or any other folder; the script has no Obsidian-specific behavior.
- **Backfill**: `tools/backfill-archive.sh <project-slug> [--base-url <url>] [--dry-run]` lists every ticket carrying the `dispatched` label via the API, recovers each one's CMS admin URL from its existing dispatch receipt comment, and runs the exact same `archive-draft.ps1` script per ticket — for drafts that were dispatched before this landed. Requires `jq`, `curl`, and `pwsh` (or `powershell` on Windows) on `PATH`, plus `GIGACLAW_ARCHIVE_ROOT` set in the environment.

## Entry points
- Hosted at app startup via DI in `GigaClaw.Web/Program.cs`.
- Per-project configuration loaded from `<workspace>/.agents/automations.json` (seeded by the [project template](./project-template.md)), plus the optional `<workspace>/.agents/workflow.json` — see [Workflow graph](./workflow-graph.md).
- Editable from the in-app **Automations** page.

## External dependencies
- [Agent dispatch](./agent-dispatch.md) — the `runAgent` action launches the `claude` CLI through it.
- [Storage](./storage.md) — reads ticket/column/comment state from per-project SQLite DBs.
- `git` on PATH — the `gitCommit` trigger polls the workspace's git log.
